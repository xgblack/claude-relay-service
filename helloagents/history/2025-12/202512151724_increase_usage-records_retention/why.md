# 变更提案: 提升调用明细保留条数到20000

## 需求背景
管理端的“请求时间线/调用明细”统计与导出依赖 Redis 中的调用明细记录 `usage:records:{keyId}`。此前默认保留条数过小（历史为 200，后提升到 5000）仍可能在高频调用场景下出现当天统计被截断的问题。

## 变更内容
1. 将 Redis 调用明细默认保留条数提升到 20000。
2. 将相关管理端接口读取上限对齐到 20000，避免“存得多但只读 5000”造成统计仍被截断。
3. 明确调用明细的过期策略与 TTL，方便运维评估存储成本与数据可追溯性。

## 影响范围
- **模块:** relay-service（Redis存储）、管理端统计接口
- **文件:**
  - `src/models/redis.js`
  - `src/routes/admin/usageTimeline.js`
  - `src/routes/admin/usageStats.js`
  - `helloagents/wiki/api.md`
  - `helloagents/CHANGELOG.md`
  - `helloagents/history/index.md`

## 核心场景

### 需求: 当天高频调用下统计不截断
**模块:** 管理端统计接口
在单 Key 或多 Key 高频调用（当天明细超过 5000 条）时，时间线页面顶部统计应尽可能覆盖当天完整范围，不应因为明细保留/读取上限过小而被截断。

#### 场景: 单 Key 时间线统计
- 前置条件：同一 API Key 当天调用量 > 5000
- 操作：进入 `/api-keys/:keyId/usage-records`
- 预期结果：顶部总费用/总请求等统计不因 5000 上限而过早截断（受全局保护上限影响时需在文档中说明）

#### 场景: 全量时间线统计
- 前置条件：多个 API Key 当天高频调用
- 操作：进入 `/usage-timeline`
- 预期结果：顶部统计尽可能覆盖当天完整范围（仍受总计 20000 条保护上限约束）

## 风险评估
- **风险:** Redis 内存占用上升（每个 Key 最多保留 20000 条 JSON 记录）。
- **缓解:** 明细依旧设置 90 天 TTL，并保留总计 20000 条查询保护上限；如需进一步控制成本，可引入配置化保留条数或按时间范围改用更适合的数据结构。
